- `Bọc EXEC cho SQL thô tham chiếu object/cột vừa tạo`: Trong EF migration, mọi `migrationBuilder.Sql(...)` chứa SQL thô (MERGE/UPDATE/INSERT/DELETE...) tham chiếu tới **bảng vừa `CreateTable`, cột vừa `AddColumn`, hoặc cột vừa `RenameColumn` (tên MỚI) trong CÙNG migration** phải bọc trong `EXEC(N'...')` (double mọi dấu `'` bên trong nếu có). Áp dụng cho cả `Up` lẫn `Down`.
    + Why: Script `dotnet ef migrations script --idempotent` gộp cả một migration vào MỘT batch không có `GO`. SQL Server compile toàn batch TRƯỚC khi chạy → SQL thô tham chiếu object/cột mà DDL phía trên chỉ tạo lúc runtime sẽ fail ngay lúc compile: bảng chưa có → `Msg 208 Invalid object name`; cột chưa có → `Msg 207 Invalid column name`. Rename cột bằng `RenameColumn` (sinh `sp_rename`) cũng vậy: tên MỚI chưa tồn tại lúc compile nên `UPDATE ... SET <tên_mới> = ...` ngay sau đó dính `Msg 207`. (DDL `CREATE/ALTER/sp_rename` tự nó compile được vì tham số là chuỗi literal; chỉ DML tham chiếu trực tiếp object/cột mới chết.) `dotnet ef database update` chạy từng command rời nên KHÔNG lộ lỗi này — chỉ lộ khi sinh script idempotent, nên dễ lọt tới production.
    + How: `EXEC(N'...')` đẩy đoạn SQL thành batch con, compile lúc execute (sau khi DDL đã thực thi). Đây đúng là cách chính EF tự dùng cho DDL động (vd `EXEC(N'ALTER TABLE ... DROP CONSTRAINT ...')`). Migration ở batch khác (sau `GO`, object đã `COMMIT` từ migration trước) thì KHÔNG cần bọc.
    + Biến thể NGƯỢC, nguy hiểm hơn hẳn: SQL thô tham chiếu cột mà **chính migration đó XOÁ** (`DropColumn`) — vd bước chuyển dữ liệu đọc cột cũ trước khi bỏ nó. Ca này chạy ngon ở mọi database CHƯA apply, và chỉ chết ở database **ĐÃ apply**: `IF NOT EXISTS(... __EFMigrationsHistory ...)` chỉ quyết định khối có CHẠY hay không, **không ngăn khối bị compile**, mà lúc đó cột đã biến mất → `Msg 207 Invalid column name`. Hậu quả là **mọi lượt deploy về sau đều hỏng**, kể cả lượt chẳng liên quan gì tới bảng đó, và triệu chứng ("Web deployment task failed... Invalid column name") không chỉ vào migration nào cả. Vì thế: **bọc `EXEC` cho MỌI `Sql()` viết tay trong migration**, đừng cân nhắc từng ca — cái giá của việc bọc thừa bằng 0.
    + Cách kiểm trước khi tin: sinh script idempotent rồi chạy nó vào **đúng database đã apply migration** (`sqlcmd -i`). Chạy sạch, không output, là đúng. Đừng kiểm bằng `dotnet ef database update` — nó chạy từng command rời nên không bao giờ lộ lỗi này.
    + Lưu ý quy trình: sau khi sửa file migration `.cs` phải BUILD lại rồi mới sinh lại script — `dotnet ef migrations script ... --no-build` dùng assembly cũ nên không phản ánh sửa đổi.
- `AddColumn cho cột enum: sửa defaultValue thành giá trị CÓ THẬT của enum`: EF sinh `AddColumn<int>(..., nullable: false, defaultValue: 0)` cho mọi cột enum không nullable. Nếu enum không có thành viên nào bằng 0 (vd `First = 1, Second = 2`), phải sửa tay `defaultValue` thành một giá trị hợp lệ trước khi apply.
    + Why: `defaultValue` không chỉ dùng để lấp các dòng đang có — nó tạo ra một **DEFAULT constraint nằm lại vĩnh viễn trên cột**. EF thường kèm `UpdateData` để sửa dòng seed nên nhìn qua tưởng đã ổn, nhưng dòng thêm bằng tay, dòng khôi phục từ sao lưu cũ, hay `INSERT` từ script ngoài đều nhận giá trị 0. Trong C# thì `(MyEnum)0` vẫn ép kiểu được, `switch` rơi vào nhánh `default`, `==` so với thành viên nào cũng false — **không có exception nào**, chỉ là hành vi âm thầm sai ở một nhánh. Model snapshot KHÔNG ghi `defaultValue` (trừ khi khai `HasDefaultValue` trong configuration), nên sửa tay con số này không gây pending-model-changes ở migration sau.
    + How: sửa thẳng `defaultValue: 0` → giá trị của thành viên mặc định (vd `defaultValue: 1`) trong file `.cs` vừa sinh, kèm comment nói rõ vì sao, rồi mới `database update`. Muốn EF tự sinh đúng ngay từ đầu thì khai `HasDefaultValue(MyEnum.First)` trong `IEntityTypeConfiguration`.

- `Đừng bật "Apply this migration on publish" của Visual Studio cho DbContext dùng SQLite`: Trong dialog Publish của VS (mục *Entity Framework Migrations*), tick một context sẽ ghi `<ItemGroup><EFMigrations Include="Namespace.MyDbContext"><Value>connection string</Value></EFMigrations></ItemGroup>` vào file `*.pubxml.user`. Lúc publish, MSBuild gọi EF sinh script **idempotent** → provider SQLite ném `System.NotSupportedException: Generating idempotent scripts for migrations is not currently supported for SQLite`, publish dừng với lỗi cụt lủn `Entity Framework SQL Script generation failed` (Line 0, không chỉ vào file nào).
    + Why: `SqliteHistoryRepository.GetEndIfScript()` không cài đặt được — SQLite không có `IF NOT EXISTS` cho khối lệnh nên EF không sinh nổi script idempotent. Chỉ SQL Server (và vài provider khác) hỗ trợ. Lỗi KHÔNG liên quan tới nội dung migration, nên đọc code migration để tìm nguyên nhân là đi sai hướng.
    + How: sửa `*.pubxml.user` xoá nguyên khối `<ItemGroup>` chứa `EFMigrations` (hoặc bỏ tick context đó trong dialog Publish → Settings). File `.user` thường bị `.gitignore` nên phải sửa trên từng máy. Với SQLite, để app tự tạo/nâng cấp schema lúc khởi động (`MigrateAsync`/`EnsureCreatedAsync`) thay vì dựa vào publish.
    + Cách tái hiện nhanh ngoài VS: `dotnet ef migrations script --idempotent --project <DbProject> --startup-project <ApiProject>` — ném đúng exception đó. Bỏ `--idempotent` thì chạy được, chứng minh nguyên nhân là cờ idempotent chứ không phải migration hỏng.

- `Một database chỉ được có ĐÚNG MỘT host gọi MigrateAsync`: Nhiều host (nhiều project ASP.NET, nhiều instance sau load balancer, worker + api...) trỏ chung một connection string mà host nào cũng `db.Database.MigrateAsync()` lúc khởi động thì bật cùng lúc sẽ ăn `Npgsql.PostgresException 23505: duplicate key value violates unique constraint "PK___EFMigrationsHistory"` (SQL Server: `Msg 2627 Violation of PRIMARY KEY constraint 'PK___EFMigrationsHistory'`).
    + Why: `MigrateAsync` đọc danh sách migration đã áp, trừ ra danh sách đang chờ, chạy chúng rồi INSERT `MigrationId` vào `__EFMigrationsHistory`. Hai tiến trình khởi động sát nhau cùng đọc ra CÙNG danh sách chờ, cùng chạy, rồi cùng INSERT một `MigrationId` — PK của bảng history là chính `MigrationId` nên tiến trình về sau chết. Triệu chứng đánh lừa ở chỗ nó **không phải lỗi của migration**: nội dung migration đúng, và mở DB ra thì thấy nó ĐÃ áp thành công (mỗi migration chạy trong một transaction riêng nên phần việc của tiến trình thua đã rollback sạch, database không hỏng — chỉ tiến trình đó chết lúc bật). Đừng đi sửa migration hay xoá dòng history.
    + How: chọn ra MỘT host làm chủ schema, các host còn lại bỏ hẳn `MigrateAsync`. Host không migrate nên thay bằng `GetPendingMigrationsAsync()` rồi log cảnh báo (bọc try/catch để DB chưa tồn tại vẫn bật được) — schema lỗi thời thì thấy ngay lúc khởi động thay vì nổ mù mờ ở request đầu tiên. Ghi luật này vào doc comment của cả hai phía, vì host thứ ba thêm sau rất dễ copy nhầm.
    + Đừng trông vào khoá của EF: từ EF Core 9 có `IMigrationsDatabaseLock` nhưng nó phụ thuộc provider có override `HistoryRepository.AcquireDatabaseLock` hay không, và không che được ca database chưa tồn tại. Kiến trúc "một chủ schema" chắc ăn hơn và không cần biết provider làm gì.

- `App đang chạy chặn "dotnet ef migrations add"? Dùng chính project Database làm startup`: `dotnet ef` luôn BUILD startup project vào thư mục bin bình thường, nên app đang debug/F5 khoá `bin/` là lệnh chỉ báo cụt lủn `Build failed. Use dotnet build to see the errors.` — chạy `dotnet build` riêng mới thấy `MSB3021 ... The file is locked by: "<App> (PID)"`.
    + How: nếu project Database có `IDesignTimeDbContextFactory<T>` thì trỏ `--startup-project` vào CHÍNH nó: `dotnet ef migrations add X --project src/Foo.Database --startup-project src/Foo.Database`. Project thư viện không ai chạy nên không bị khoá, và factory đã tự cấp connection string design-time nên không cần host thật. Không có factory thì thêm một cái (đọc connection string từ file cấu hình design-time riêng) — nó có ích lâu dài hơn là mỗi lần lại đi tắt app.
    + Đừng chữa bằng `--no-build`: nó dùng assembly CŨ trong bin, nên migration sinh ra so với model chưa có thay đổi vừa sửa và ra rỗng — sai âm thầm, tệ hơn hẳn build lỗi.
    + Sinh nhầm rồi thì `dotnet ef migrations remove` rồi sinh lại, ĐỪNG sửa tay file `.cs`: `.Designer.cs` và `ModelSnapshot.cs` cũng phải đổi theo, sửa thiếu một chỗ là migration kế tiếp diff sai.
    + **`migrations remove` lại càng KHÔNG được `--no-build`, và cái giá ở đây là MẤT VIỆC chứ không phải file rỗng.** `remove` xoá "migration cuối cùng" theo assembly trong `bin`; mà `migrations add` thì BUILD trước khi sinh file, nên ngay sau một `add`, bin đã chứa migration mới — còn `remove --no-build` nạp lại đúng assembly ấy hoặc một bản cũ hơn và xoá nhầm **migration liền trước**, kéo `ModelSnapshot.cs` revert theo. Gặp thật 21/9/2026: một agent kiểm "snapshot có lệch không" bằng cách `add __check` rồi `remove --no-build`, và nó xoá mất migration thật vừa viết xong của đợt trước đó.
    + Mẹo kiểm "snapshot có khớp cấu hình EF không" cho an toàn: `dotnet ef migrations add __check` (CÓ build) → mở file xem `Up`/`Down` có RỖNG không → `dotnet ef migrations remove` (CŨNG có build). Xong thì `git status` đối chiếu để chắc không sót dấu vết — nhất là `ModelSnapshot.cs`.
